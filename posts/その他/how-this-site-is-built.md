## 要約

research-as-code は Markdown・静的サイト生成・AWS配信という最小構成で作られている。このサイト自体を「Infrastructure as Code」の実例として公開する。

研究のワークフローを Word や Excel から Markdown・DB・プログラムへ置き換えるべきだ、という問題提起をこのサイトは掲げています。その考え方は、サイト自体の作り方にもそのまま反映されています。

## なぜこの構成にしたか

個人運営・自己研鑽という前提に対して、次の3つを優先しました。

- **安価**であること（ドメイン代以外はほぼ無料枠で収まる規模）
- **運用が軽い**こと（サーバーの保守が発生しない）
- **変更履歴が追える**こと（インフラも記事も、変更がすべてGitで残る）

動的なバックエンド（Lambda・API Gateway・DynamoDBなど）は初期構成にはあえて含めていません。必要になったときに追加すればよい、という考え方です。

## 技術構成

| レイヤー | 技術 | 役割 |
|---|---|---|
| 原稿管理 | GitHub（記事用リポジトリ） | 記事のバージョン管理 |
| サイト生成 | Next.js（完全SSG） | ビルド時に記事を取り込みHTML化 |
| 検索 | Pagefind | クライアントサイド完結の全文検索 |
| ホスティング | S3 | ビルド済み成果物の配置場所 |
| 配信 | CloudFront | S3前段のキャッシュ配信 |
| インフラ管理 | AWS CDK | インフラをコードとして管理 |

## リポジトリを記事用とサイト用で分けている理由

このサイトの実装は `research-as-code` リポジトリに、記事本文はこの `research-as-code-articles` リポジトリに分かれています。

分ける理由はシンプルです。

- 記事を書く人（将来的な寄稿者を含む）には、この記事用リポジトリだけ渡せば済む
- ビルド設定やインフラのコードを誤って触ってしまうリスクが減る
- 将来、記事の管理方法を変える（例えばHeadless CMSに移行する）ときも、記事用リポジトリの差し替えだけで済む

## データが流れる仕組み

1. この記事用リポジトリにMarkdownをpushする
2. サイト側のビルドパイプラインがそれを検知し、記事を取り込んでビルドする
3. ビルドした静的ファイルをS3にアップロードする
4. CloudFront経由で読者に配信する

サーバーが常時動いているわけではなく、記事が更新されるたびに静的なHTMLが作り直されて配信される、という仕組みです。

## これから

まずは記事を書き続けること、そして検索機能を段階的に足していくことを予定しています。将来的には記事の募集（寄稿の受け入れ）や、動的なツールの追加も検討していきます。
